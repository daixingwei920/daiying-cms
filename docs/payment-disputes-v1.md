# Verified payment disputes — isolated candidate contract

Core version remains 1.2.83. This contract is present only in the B/C candidate build; it is not part of the unchanged official v1.2.83 artifact.

A trusted payment provider registered through PluginContext may additionally implement `PaymentDisputeProviderInterface`. Existing `POST /payment/webhooks/{provider}` retains size, provider-enabled and response-security handling. `isDisputeWebhook()` only routes a payload: it does not authenticate it. `verifyDisputeWebhook()` MUST validate the channel-specific signature, timestamp/replay window and event identity before returning normalized facts. Public provider configuration must contain the verified account's `merchant_id`. Secrets remain in existing encrypted settings.

Normalized facts: `provider_id`, `merchant_id`, `provider_payment_id` (Core remote payment reference), `subject_type`, `subject_id`, `dispute_id`, `event_id`, `state`, `outcome`, and optional integer `sequence`. References are bounded ASCII identifiers. States: open / under_review / closed / unknown. Outcomes: won / lost / unknown. `closed` alone never implies won; nonclosed outcomes are unknown. `closed/lost` is terminal. Multiple disputes aggregate: ANY state other than closed/won blocks.

`hasReliableDisputeSequence()` is true only when the provider guarantees an authenticated strictly ordered per-dispute integer. Otherwise Core calls `fetchDisputeSnapshot()` outside the DB lock and compares revision again under lock. Callback timestamps never resolve ordering. Failed or mismatched lookup creates an unknown hold and 503 retry; the same pending event may be verified again. Overlapping stale lookup returns 409. Reliable lower sequence is ignored; equal conflicting sequence is rejected. Provider+event is unique and conflicting payload hashes fail closed.

New tables, migration `2026_10_13_000002_payment_disputes`: `cms_payment_disputes`, `cms_payment_dispute_events`. Core binds provider, merchant, payment and subject, owns the ingress transaction, and commits dispute state with existing public payment webhook receipt operations. Ingress refuses a caller-owned transaction. No network while holding its DB lock. MySQL reads during restoration are locking/current reads, including dispute and refund rows. Receipt placeholder aliases are distinct with native PDO preparation.

Public read-only `PaymentService::disputeSnapshot(paymentId)` returns payment/provider/subject association, payment state and paid time, amount/currency/net/refund totals, necessary dispute IDs/state/outcome/revision/verified_at, aggregate blocking and revision. It contains no merchant secrets or raw gateway payload. With a caller-owned transaction it locks the payment row for consistency with ingress/refunds. `PaymentDisputeChangedEvent(paymentId, providerId)` is only a post-commit reconciliation hint. Consumers MUST re-read the snapshot; repeated delivery is safe. Notification failure is audited and periodic business reconciliation remains necessary.

Core redacted audit actions: applied / stale / verification_pending / rejected / notification_failed. Warnings do not include raw signatures, secrets or gateway bodies. Audit subsystem failure is logged generically. Consumers keep explicit hold/error states when snapshot validation is unavailable.

The shipped merchant providers have not been adapted in this change. `tests/fixtures/CoreDisputeFixtureProvider.php` is a no-network test provider, not a merchant gateway and never a bundled production plugin. Live merchant dispute verification is NOT VERIFIED. Deploying this candidate or enabling any real provider requires separate approval and channel-specific validation.
