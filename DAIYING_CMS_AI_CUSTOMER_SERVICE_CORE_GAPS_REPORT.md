# Daiying CMS AI Customer Service Core Gaps Report

Date: 2026-09-15
Core candidate version: 1.2.62

## Scope

This task only closes two generic Core gaps required by `official.ai-customer-service`:

- official plugin trust registration
- generic frontend extension / asset mount

No AI customer service business code, prompt, RAG, knowledge-base logic, chat UI, or theme file was changed.

## 1. Official Plugin Trust

Current Core already protects official/trusted plugins through:

- `system/core/Plugin/OfficialPluginRegistry.php`
- root operational support registry `system/official-plugins.php`
- `PluginManager::discover()`
- `PluginManager::syncDiscovered()`
- `LocalPluginPackageInstaller::enable()`
- Marketplace Trust Grant handling for official market packages

The trust lifecycle remains unchanged:

1. `official.*`, `bundled`, `system-plugin`, or `trusted_php` claims are rejected unless Core can prove the plugin is a trusted bundled official plugin or a signed official market package.
2. Ordinary third-party plugins cannot claim `official.*` or `trusted_php`.
3. Reserved database prefixes remain protected.

### Registered Plugin

`official.ai-customer-service` was registered in the unified official registry:

- directory: `official.ai-customer-service`
- package type: `plugin`
- trust level: `trusted_php`
- capability namespace: `ai_customer_service`
- table prefix: `ai_customer_service_`

This is a normal registry entry, not an AI customer service installer special case.

## 2. Generic Frontend Extension API

Added a generic frontend extension API for enabled plugins:

- capability: `frontend.asset`
- `PluginContext::frontendScript(string $relativePath, string $key = '', array $attributes = [])`
- `PluginContext::frontendStyle(string $relativePath, string $key = '', array $attributes = [])`
- `PluginContext::frontendBodyEnd(callable $callback, string $key = '')`
- runtime storage: `PluginRuntimeRegistry`
- response injection: `FrontendExtensionRenderer`

The API is intentionally generic and can be reused by:

- AI customer service
- cookie consent
- analytics
- floating frontend tools
- accessibility helpers
- other frontend plugin JS/CSS extensions

## 3. HTML Response Rules

Frontend extension snippets are injected only when all of the following are true:

- request method is `GET`
- response status is 2xx
- response content type contains `text/html`
- response is not a redirect
- response is not a download-style response
- path is not `/admin` or `/admin/...`
- path is not `/api` or `/api/...`
- path is not `/extension-assets/...`
- path is not `/health`, `/sitemap.xml`, `/robots.txt`, or `/ads.txt`

The renderer does not inject into JSON, XML, redirects, admin pages, extension assets, health checks, or HEAD requests.

## 4. Asset Security

Frontend scripts and styles must be registered through `PluginContext`, which generates URLs through:

- `PluginContext::assetUrl()`
- `ExtensionAssetController::url()`

`PluginRuntimeRegistry` rejects plugin frontend asset URLs that do not use the Core extension asset endpoint for the same plugin ID.

Recommended AI customer service plugin usage:

```php
$context->frontendScript('public/ai-customer-service/mount.js', 'mount');
```

The actual browser URL is generated by Core as:

```text
/extension-assets/plugin/official.ai-customer-service?file=public%2Fai-customer-service%2Fmount.js&v=...
```

## 5. Exception Isolation

Frontend body-end callbacks are wrapped individually.

If one plugin callback throws:

- the exception is logged as `Plugin frontend extension failed`
- the page still returns normally
- other plugin assets and snippets continue to render
- the response is not converted to HTTP 500

## 6. Deduplication

Assets and snippets are deduplicated by key:

- explicit keys are namespaced by plugin ID
- assets without explicit keys are deduplicated by type and URL
- repeated `frontendScript(..., 'mount')` emits only one script tag

## 7. Theme Compatibility

Regression testing used a plain HTML theme response with no AI customer service code. After the plugin is enabled, Core injects the mount script at body end. After the plugin is disabled, the mount script is no longer injected.

Themes do not need to edit footer templates, add shortcodes, add blocks, or know `official.ai-customer-service` exists.

## 8. Public API Contract

`PublicApiRegistry` now lists:

- `frontend.extensions`
- `plugin.context` with `frontend.asset`

This marks the extension point as a stable Core public API surface for plugins.

## 12. AI Customer Service Thread Handoff

After this Core version is available, the AI customer service plugin should:

1. Keep its plugin ID as `official.ai-customer-service`.
2. Declare `frontend.asset` in `plugin.json`.
3. Keep custom capabilities under `ai_customer_service.*`.
4. Keep plugin-owned tables under `ai_customer_service_`.
5. Register the frontend mount script during plugin boot:

```php
$context->frontendScript('public/ai-customer-service/mount.js', 'mount');
```

The plugin must not ask themes to edit templates for first-run mounting.

## 13. Risks / Notes

- Existing plugins using custom frontend routes for JS can keep them, but the recommended stable Core mechanism is now `frontendScript()` with extension assets.
- This implementation does not expose frontend injection to admin pages by default.
- This implementation does not change Marketplace Trust Grant semantics.
